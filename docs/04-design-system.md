## 1. 🔴 กฎที่สำคัญที่สุด — แดงเป็นช่วงเวลา ไม่ใช่พื้นผิว

แดงคือสีแบรนด์ยามาฮ่า แต่บลูพรินต์ห้ามเอาสีเน้นไปถมเป็นพื้นผิว
ทางออกคือใช้แบบเดียวกับตัวอย่าง `.cta` ของบลูพรินต์เอง — **พิลล์หมึก + รายละเอียดสีเน้น**

| ที่ | ใช้อะไร |
|---|---|
| ปุ่มหลัก | พื้น**หมึก** `#16181D` + **ลูกศรแดง** |
| เมนูที่เลือก | พื้นขาว + **ขีดแดง 2px ด้านซ้าย** + ไอคอนแดง |
| แท็บที่เลือก | **ขีดแดง 2px ใต้ข้อความ** |
| กราฟแท่ง | **หมึก** — แดงเฉพาะแท่งที่เกินเกณฑ์ |
| แถบโปรโมชัน | การ์ดขาว + **จุดแดง** |
| แดงใช้ที่เหลือ | ลิงก์ · focus ring · โลโก้ · ตัวเลขที่ต้องรีบจัดการ |

**ผลพลอยได้:** แดงหลุดจากการเป็นสี "ผิดพลาด" ได้จริง — ปัญหาที่บันทึกไว้ใน `01-gap-analysis.md` §4.7
ตอนนี้สถานะสื่อด้วย **ข้อความ + จุดสี ไม่มีพื้นสี** ซึ่งสงบตากว่าและอ่านง่ายกว่า

## 2. Token ทั้งหมด

```css
:root{
  /* Canvas */
  --paper:#FAFAF8;  --paper-2:#F4F3EF;  --card:#FFFFFF;  --dark:#0E0F12;

  /* Ink — หมึกหนึ่ง หมึกอ่อนหนึ่ง เทาหนึ่ง */
  --ink:#16181D;  --ink-soft:#3A3E47;  --muted:#8B8F98;
  --hairline:rgba(22,24,29,.12);  --hairline-2:rgba(22,24,29,.06);
  --hairline-dark:rgba(255,255,255,.10);

  /* Accent — หนึ่งเดียว สองตัวแปร */
  --accent:#E60012;  --accent-hover:#FF2B39;  --accent-deep:#B3000E;
  --accent-wash:rgba(230,0,18,.06);

  /* สถานะ — ข้อความกับจุด ไม่มีพื้นสี */
  --pos:#1F7A4D;  --attn:#A96410;

  /* Spacing — 8-point */
  --s-half:4px; --s1:8px; --s2:16px; --s3:24px; --s4:32px; --s5:48px; --s6:64px;

  /* Radii */
  --r-input:8px; --r-card:12px; --r-lg:16px; --r-btn:24px; --r-pill:999px;

  /* Shadow — ย้อมสีหมึก ไม่ใช่ดำล้วน */
  --sh-sm:0 1px 2px rgba(22,24,29,.06);
  --sh-md:0 8px 24px rgba(22,24,29,.10);
  --sh-lg:0 20px 50px rgba(22,24,29,.16);
  --glow:0 0 30px rgba(230,0,18,.28);

  /* Type — แปดขนาด */
  --t-label:12px; --t-table:14px; --t-body:15px; --t-lead:18px;
  --t-h2:20px; --t-h1:28px; --t-stat:32px; --t-display:34px;

  /* Font */
  --f-display:'Trirong', Georgia, serif;
  --f-body:'Inter', 'Anuphan', system-ui, sans-serif;

  /* Motion */
  --ease:cubic-bezier(.16,1,.3,1); --dur-ui:.3s; --dur-in:1s;
}
```

> `--s-half` (4px) เป็นครึ่งขั้นที่อนุญาตไว้เฉพาะช่องไฟภายในคอนโทรลเล็ก
> ส่วนจังหวะของเลย์เอาต์ใช้ 8-point เท่านั้น

## 3. ตัวอักษร

| บทบาท | ฟอนต์ | ใช้กับ |
|---|---|---|
| Display | **Trirong** (serif ไทย+ละติน) | ชื่อหน้า · หัวการ์ด · ตัวเลข KPI · หัวเอกสาร · โลโก้ |
| Body | **Inter** + **Anuphan** | เนื้อหา ตาราง ฟอร์ม เมนู |
| สลับได้ | **Sarabun** | ปุ่มสลับฟอนต์มีหัว |

**เหตุผล** — Anuphan ออกแบบมาเพื่อหน้าจอ x-height สูง ช่องเปิดกว้าง อ่านง่ายกว่า IBM Plex Sans Thai
ที่ v0.5–0.6 ใช้ · Inter ให้ตัวเลข tabular ที่จำเป็นกับตารางเงิน · Trirong เพิ่มบุคลิกแบบสิ่งพิมพ์
ซึ่งเป็นสิ่งที่ทำให้หน้าจอ**ไม่ดูเหมือนงานที่ AI ปั๊มออกมา** (ซึ่งมักใช้ sans ตัวเดียวทั้งหน้า)

| Token | ขนาด | line-height | tracking | ตระกูล |
|---|---|---|---|---|
| label | 12 | 1.3 | +0.06em | sans |
| table | 14 | 1.5 | 0 | sans |
| body | 15 | 1.6 | 0 | sans |
| lead | 18 | 1.5 | 0 | sans |
| h2 | 20 | 1.3 | −0.01em | serif |
| h1 | 28 | 1.15 | −0.02em | serif |
| stat | 32 | 1.05 | −0.02em | serif |
| display | 34 | 1.0 | −0.02em | serif |

**กฎ:** ตัวใหญ่ขึ้น → line-height แน่นขึ้น · tracking สวนทางกับขนาด · ตัวเลขทุกที่ใช้ `tabular-nums`

## 4. การแยกพื้นผิว — เลือกอย่างแรกที่ใช้ได้ ห้ามซ้อน

```
1. FILL    ← พื้นที่ต่างสีกัน (ถูกที่สุด สงบที่สุด)
2. SHADOW  ← ถ้า fill ไม่พอ ค่อยยกขึ้น
3. BORDER  ← เฉพาะเมื่อต้องอยู่ระนาบเดียวกันจริง ๆ
```

| องค์ประกอบ | ใช้ |
|---|---|
| การ์ด | พื้นขาวบนกระดาษอุ่น + `--sh-sm` — **ไม่มีเส้นขอบ** |
| ตาราง | hairline อย่างเดียว — **ไม่มีพื้นหัวตาราง** |
| แถวข้างในการ์ด | **เส้นคั่นอย่างเดียว ไม่มีพื้น** (v1.7 — ดูข้อ 9c) |
| ฟอร์ม | เส้นขอบ hairline อย่างเดียว |

> v0.6 ซ้อน fill + border + shadow บน `.card` และ `.kpi` พร้อมกัน — บลูพรินต์เรียกสิ่งนี้ว่า
> *"สัญญาณที่ชัดที่สุดของงานสมัครเล่น"* v0.7 แก้แล้ว

## 6. การเคลื่อนไหว

```css
--ease:cubic-bezier(.16,1,.3,1);   /* เส้นโค้งเดียวทั้งระบบ */
--dur-ui:.3s;                      /* ตอบสนอง UI */
--dur-in:1s;                       /* เข้าหน้า */
```

- เข้าหน้า: จาง + เลื่อนขึ้น 24px · ไล่ทีละการ์ด 0.08s
- hover ลิงก์: ลด opacity เป็น 0.6 — **ไม่เปลี่ยนสี**
- กดปุ่ม: `scale(.97)`
- ไม่มี bounce ไม่มี spring
- `prefers-reduced-motion` ปิดทั้งหมด

## 8. มือถือคือจอหลัก (v1.2–v1.4)

เจ้าของร้านใช้งานจริงบนมือถือเป็นหลัก เดสก์ท็อปเป็นรอง กฎทั้งหมดในหัวข้อนี้บังคับที่ **≤900px**
(เปลือกแอป) และ **≤600px** (การจัดวางเนื้อหา) — เดสก์ท็อป ≥901px ไม่เปลี่ยนจากเดิม

| เรื่อง | กฎ |
|---|---|
| **การเลื่อน** | **ห้ามมีการเลื่อนซ้าย-ขวาทุกจอ** — นิ้วโป้งเลื่อนขึ้น-ลงอย่างเดียว ยกเว้น `.doc` (ตัวอย่างเอกสาร A4) |
| เมนู | แถบล่างตามบทบาท + ปุ่มลอยงานหลัก + แผ่น "อื่น ๆ" — ไม่มี sidebar |
| ตาราง | ทุกตารางแสดงเป็นการ์ด: หัวเรื่อง + ตัวเลขสำคัญ + บรรทัดรายละเอียด + แถวปุ่ม |
| ตาราง 2 มิติ | เปลี่ยนเป็นรายการมิติเดียว โดยให้เลือกมิติหนึ่งก่อน (เช่น เลือกจำนวนงวด → รายการไฟแนนซ์) |
| แท็บ | ชิปพับหลายบรรทัด เห็นครบทุกอัน · ตัวที่เลือกเป็นชิปทึบ ไม่ใช่ขีดใต้ |
| คัมบัง | ชิปเลือกขั้นตอน (บอกจำนวนงาน) + รายการเต็มความกว้าง |
| ตัวกรอง ≥2 ช่อง | ยุบเป็นปุ่ม "ตัวกรอง" เปิดแผ่นล่าง + บรรทัดสรุปว่ากรองอะไรอยู่ |
| ปุ่ม/เป้าแตะ | ≥44px (ปุ่มรอง ≥40px) · input ≥16px กัน iOS ซูมเอง |
| กล่องซ้อน | drawer/modal เป็น bottom sheet + ล็อก scroll พื้นหลัง |
| KPI | ตัวเลขไม่ตกบรรทัด (ย่อขนาดตามความกว้างจอแทน) |

**วิธีตรวจ:** สคริปต์กวาดทุก element ในทุกหน้าจอ × ทุกบทบาท ที่ 390px แล้วยืนยันว่าไม่มีตัวไหน
`overflow-x` เป็น auto/scroll พร้อมเนื้อกว้างเกินกรอบ (ตัวที่ตัดข้อความด้วย ellipsis ไม่นับ
เพราะผู้ใช้ปัดไม่ได้) — เกณฑ์นี้ต้องผ่านก่อนทุกครั้งที่ push

## 9. หลักฐานที่ตรวจสอบย้อนกลับได้ (v1.5)

ตั้งแต่รอบลงเวลาเป็นต้นไป ทุกอย่างที่ **กลายเป็นเงิน** ต้องตรวจย้อนกลับได้ กฎ 5 ข้อ:

| กฎ | เหตุผล | ที่ทำจริง |
|---|---|---|
| ~~**บันทึกเวลาก่อน แล้วค่อยเก็บหลักฐาน**~~ **ถูกยกเลิกใน v1.8 — ดูข้อ 9d** | ของเดิมจับเวลาหลังรอกล้อง+GPS ทำให้ช้ากว่าที่กดจริงถึง ~4 วินาที | เคยเป็น `punch()` เขียนเวลาแบบ sync แล้ว `attProof()` วิ่งเบื้องหลังตามมาแนบ |
| **เก็บถึงวินาที และวินาทีต้องมีผลจริง** | ถ้าโชว์วินาทีแต่ปัดทิ้งตอนคิดเงิน ก็เท่ากับหลอกผู้ใช้ | ทุกสูตรผ่าน `toSec()` · `attCalc()` เป็นจุดคำนวณจุดเดียว |
| **ไม่มีบันทึก = ไม่มีชั่วโมง** | ของเดิมแถม 8 ชม. ให้คนไม่ตอกบัตร ตัวเลขจึงเชื่อไม่ได้ | `attMonth()` รวมจากบันทึกจริง วันที่ขาดขึ้นเป็นคำเตือน ไม่หักเงินเอง |
| **แก้ได้ แต่ลบไม่ได้** | ผู้จัดการต้องแก้เวลาที่ผิดได้ โดยไม่ทำให้ประวัติหาย | `editLog` เก็บว่าใครแก้ เวลาไหน จากค่าเดิมเป็นอะไร เพราะอะไร |
| **หลักฐานต้องอยู่นานพอ แต่ไม่กินเครื่อง** | รูปทุกวัน × 9 คน × ทั้งปี = หนักเกินไปถ้าเก็บขนาดเต็มหมด | 3 ชั้นตามอายุ: สด 640×480 → เกิน 30 วัน 384×288 → เกิน 1 ปีลบรูป เวลายังอยู่ |

รูปเก็บใน **IndexedDB** (`attphoto`) ไม่ใช่ในอาร์เรย์ข้อมูล — `ATT` เก็บแค่ `photoId`
เบราว์เซอร์ที่ใช้ IndexedDB ไม่ได้จะถอยไปเก็บในหน่วยความจำ **และบอกผู้ใช้ตรง ๆ** ว่ารูปจะหาย

**คิวตรวจของผู้จัดการ** ขึ้นเฉพาะบันทึกที่มีธง (สาย · OT · ลืมลงเวลาออก · ถูกแก้)
บันทึกปกติไม่เข้าคิว — ไม่งั้นผู้จัดการต้องกดยืนยันวันละ 9 ครั้งโดยไม่ได้ข้อมูลเพิ่ม

## 9b. ใครเห็นอะไร — กฎความเป็นส่วนตัวของข้อมูลพนักงาน (v1.6)

เดิมการกันข้อมูลทำด้วย **สาขา** อย่างเดียว (`inScope`) พนักงานในสาขาเดียวกันจึงเห็นเวลาเข้า-ออก
รูปถ่าย พิกัด และใบลาของกันและกันหมด รอบนี้เพิ่มมิติที่สอง: **เป็นของฉันเองหรือไม่**

| ข้อมูล | แอดมิน · ผู้บริหาร · ฝ่ายบุคคล | เซลล์ · สต๊อก · ช่าง · บัญชี |
|---|---|---|
| เวลาเข้า-ออกของทีม | เห็นทั้งสาขาที่ตัวเองเห็นได้ | **เห็นเฉพาะของตัวเอง** |
| รูปถ่าย · พิกัด · อุปกรณ์ | เห็นเพื่อตรวจ | **เฉพาะของตัวเอง** (ของคนอื่นขึ้นไอคอนกุญแจ) |

## 9e. รูปที่บันทึกต้องเป็นภาพเดียวกับที่เห็นในกรอบ (v1.9)

เจ้าของแจ้งว่า *"กล้องไม่ตรงกับรูปที่ถ่ายจริง และอยากให้ revert กล้องซ้าย-ขวาด้วย"*

กรอบพรีวิว `.psCam` เป็น 4:3 และ `<video>` ข้างในใช้ `object-fit:cover` คือ **ครอปตรงกลาง**
แต่ `camSnap()` เดิมสั่ง `drawImage(video,0,0,w,h)` ซึ่งยัดทั้งเฟรมลงกรอบ
กล้องหน้ามือถือส่วนใหญ่ส่ง 16:9 มา ภาพที่บันทึกจึงถูกบีบแบนและติดขอบข้างที่พรีวิวไม่เคยแสดง

**กฎ — พรีวิวกับไฟล์ที่บันทึกต้องผ่านการแปลงชุดเดียวกันเสมอ**
ถ้า CSS ครอปหรือพลิกอะไร `camSnap()` ต้องทำอย่างเดียวกันลงพิกเซล

| ทำที่ไหน | ครอปกลางแบบ cover | พลิกซ้าย-ขวา |
|---|---|---|
| ภาพสด `<video>` | `object-fit:cover` | `.psCam video{ transform:scaleX(-1) }` |
| ตอนถ่าย `camSnap()` | `scale=Math.max(w/vw,h/vh)` แล้วส่ง `sx,sy,sw,sh` เข้า `drawImage` | `g.translate(w,0); g.scale(-1,1)` |
| ภาพนิ่ง `<img>` | `object-fit:cover` (ภาพเป็น 4:3 อยู่แล้ว จึงไม่ครอปซ้ำ) | **ไม่พลิก** — `camSnap` พลิกลงพิกเซลไปแล้ว |

แถวสุดท้ายคือจุดที่พลาดง่ายที่สุด ถ้าใส่ `transform:scaleX(-1)` ให้ `.psCam img` ด้วย
ภาพจะพลิกสองครั้งแล้วกลับไปตรงข้ามกับที่ผู้ใช้เพิ่งเห็น กฎ CSS จึงเจาะจง `video` เท่านั้น

**ผลข้างเคียงที่ยอมรับแล้ว** รูปหลักฐานเป็นภาพกระจกเงา ป้ายหรือตัวหนังสือในฉากจะกลับด้าน
เลือกแบบนี้เพราะคำสั่งคือให้รูปตรงกับพรีวิว **และ** ให้พลิกซ้าย-ขวา — พร้อมกันได้ทางเดียวคือพลิกทั้งคู่

**ด่านตรวจ** `cam-r8.js` — กล้องปลอมวาดเองจาก `canvas.captureStream()` เป็นแถบสี 4 แถบ
รัน 3 อัตราส่วน (4:3 · 16:9 · 9:16) แล้วอ่านสีกลับจาก dataURL ที่เก็บลง IndexedDB จริง
จุดอ่านที่ 0.22/0.78 เป็นข้อชี้ขาดว่า "ครอป" หรือ "ยัดทั้งเฟรม" เพราะจุดกลางแถบทั้งสี่แยกสองแบบนี้ไม่ออก

## 9f. เส้นทางที่มีขั้นตอน = แถบเลขขั้น ไม่ใช่กระดานคัมบัง (v1.10)

เจ้าของสั่งเรื่องงานติดตามลูกค้าว่า *"ไม่ต้องเป็น kanban แต่อยากได้เป็น ui ที่เป็น progress แทน
เช่นมี 5 ขั้นตอน ก็จะขึ้นเป็นแบบ เลข 1-5 แล้วแถบจะขยับไปขั้นต่อไปตอนเรามี action แล้ว"*

**กฎ — เส้นทางที่ผู้ใช้ต้องเดินทีละขั้นให้แสดงเป็น `steps()` ไม่ใช่ป้ายสถานะเดี่ยว ๆ**
ป้ายสถานะบอกได้แค่ "ตอนนี้อยู่ตรงไหน" แต่ไม่บอก "มาไกลแค่ไหน เหลืออีกกี่ขั้น"
ซึ่งเป็นสิ่งที่คนติดตามลูกค้าต้องรู้ก่อน

`steps(track, i, o)` — ดูที่ `index.html` ส่วนตัวช่วย UI

| อาร์กิวเมนต์ | ความหมาย |
|---|---|
| `track` | ชื่อขั้นเรียงตามลำดับจริง **ต้องเป็นเส้นตรง ไม่มีทางแยก** |
| `i` | ดัชนีขั้นปัจจุบัน นับจาก 0 |
| `o.off` | ตกราง — ขั้นปัจจุบันเป็นวงแดงกลวง ไม่นับว่าเดินต่อ |
| `o.act` | ฟังก์ชันคืน attribute ให้ปุ่ม ใส่แล้วกดเลื่อนขั้นได้ · ไม่ใส่คือแสดงอย่างเดียว |
| `o.lab` | โชว์ชื่อขั้นใต้ตัวเลข ใช้ในแผ่นรายละเอียดที่มีที่ว่างพอ |

**ข้อบังคับสามข้อ**

1. **`track` ต้องเป็นเส้นตรงจริง ๆ** — สถานะที่เป็น "ทางตัน" ห้ามแทรกกลางลิสต์
   ของเดิม `CUST_STAGES` เก็บ `'ไม่ผ่าน'` ไว้ระหว่าง `'ผ่าน'` กับ `'รับรถสำเร็จ'`
   ปุ่มขั้นถัดไปจาก "ผ่าน" จึงเด้งไป "ไม่ผ่าน" และจาก "ไม่ผ่าน" เด้งไป "รับรถสำเร็จ"
   ทั้งสองทางไม่มีอยู่จริงในธุรกิจ → แยกเป็น `CUST_TRACK` (5 ขั้น) + `CUST_OFF` (ตกราง)
2. **ปุ่มวาดเฉพาะขั้นที่ติดกัน ±1 และด่านต้องอยู่ในฟังก์ชันด้วย** (ตามข้อ 9b)
   `custMove()` เช็ก `Math.abs(ix-st.i)!==1` เองอีกชั้น — ปุ่มที่ไม่ได้วาดยังถูกเรียกจากที่อื่นได้

**เรื่องกล่อง** แถบนี้ไม่เพิ่มชั้นกล่องเลยตามข้อ 9c — มีแค่วงไอคอน เส้นเชื่อม และสี

## 9g. งานหนึ่งชิ้น = หน้าเดียว และขั้นตอนต้อง "คิดจากข้อมูล" ไม่ใช่ "เก็บไว้" (v1.11)

เจ้าของสั่ง: *"รวมการจัดการลูกค้าเป็นหน้าเดียว(ขายรถ, ทะเบียน, ไฟแนนซ์)
เพื่อให้ง่ายต่อการใข้งานและเป็น ux ที่ดี ไม่ซับซ้อน"*

### อาการที่วัดได้ ไม่ใช่แค่ความรู้สึก

ของเดิมงานลูกค้าหนึ่งรายกระจายอยู่ 4 หน้าที่ต่างคนต่างมีชุดขั้นตอนของตัวเอง —
ลูกค้า 5 ขั้น · ทะเบียน 6 ขั้น · เคสสินเชื่อ 5 ขั้น — และมี `syncFinToReg()`
คอยไล่ให้ตรงกัน ทำงานหนึ่งอย่างจึงต้องเดินสามจังหวะทุกครั้ง:

```js
onclick=()=>{ closeDrawer(); go('fin'); setTimeout(()=>finDrawer(id),150); }
```

**ปิดแผ่น → ข้ามหน้า → เปิดแผ่นใหม่** นี่คือความซับซ้อนที่ต้องแก้ ไม่ใช่จำนวนปุ่ม

### กฎที่ได้จากรอบนี้

**1 · ขั้นตอนต้องคำนวณจากระเบียนจริง ห้ามเก็บเป็นฟิลด์ที่สาม**

`dealOf(custId)` อ่านจาก `SALES` / `FINCASES` / `REGS` ที่เป็นเจ้าของข้อมูลอยู่แล้ว
แล้วคืนขั้นปัจจุบันออกมา ปุ่มทุกปุ่มเขียนลงระเบียนเดิมผ่าน `finAdvance()` / `regAdvance()` ฯลฯ
**จึงไม่มีทางที่ความจริงสองชุดจะหลุดจากกัน** ถ้าเก็บ `deal.stage` เพิ่มเมื่อไหร่
ก็ต้องมี sync อีกตัวทันที และ sync คือที่ที่บั๊กอยู่

ลำดับการตัดสิน — เจอข้อไหนก่อนใช้ข้อนั้น:

| เงื่อนไข | ขั้น |
|---|---|
| `rg.stage === 'ส่งมอบแล้ว'` | ส่งมอบ |
| จ่ายผ่อน และเคสสินเชื่อยังไม่ `'อนุมัติแล้ว'` | ไฟแนนซ์ (`'ปฏิเสธ'` → ตกราง) |
| มีการขาย | ทะเบียน |
| ไม่มีการขาย | คุยกับลูกค้า |

**2 · ขั้นที่ไม่เกี่ยวกับดีลนั้น ให้ตัดออกจากเส้นทางไปเลย**
ดีลเงินสดได้ 4 ขั้น ไม่ใช่ 5 ขั้นแล้วเขียนกำกับว่า "ข้าม" —
`steps()` รับ track ยาวเท่าไหร่ก็ได้อยู่แล้ว การโชว์ขั้นที่ไม่มีวันเกิดคือการเพิ่มสิ่งที่ต้องอ่าน

**3 · โชว์เฉพาะปุ่มของขั้นปัจจุบัน**
บล็อก "ต้องทำต่อ" มีแค่สิ่งที่ทำได้ตอนนี้ ไม่ใช่ทุกปุ่มที่มีในระบบ
ผู้ใช้จึงไม่ต้องเลือกว่าอันไหนใช่ และปุ่มเขียนบอกตรง ๆ ว่าจะไปขั้นไหน (`ไป: รอทะเบียน →`)
ไม่ใช่ `▶` ที่ต้องเดา

**4 · แถบความคืบหน้าเป็นตัวบอกสถานะ ไม่ใช่ปุ่ม**
v1.10 เคยทำให้กดเลขขั้นเพื่อเลื่อนได้ พอมีบล็อก "ต้องทำต่อ" แล้วจะกลายเป็นสองทางทำสิ่งเดียวกัน
ซึ่งคือความซับซ้อนที่กำลังแก้อยู่ — จึงถอด `o.act` ออกจาก `steps()`

**5 · ทางออกฉุกเฉินต้องจางกว่าปุ่มหลัก**
"ยกเลิกการขาย" อยู่คนละบรรทัดแบบ `btn ghost` สีแดง ไม่ใช่ `btn dgr` ข้างปุ่มหลัก
ปุ่มแดงเข้มสองใบในแถวเดียวทำให้ไม่รู้ว่าอันไหนคือทางปกติ

**6 · ของที่เป็น "การตั้งค่า" ให้อยู่หน้าตั้งค่า**
แท็บบริษัทไฟแนนซ์ย้ายจากหน้าเคสสินเชื่อไปอยู่กับ "รุ่นรถและสี"
เอกสารย้ายจากแท็บในหน้าขายรถมาอยู่ในหน้าดีล เพราะเอกสารเป็นของดีล ไม่ใช่ของฟอร์มที่กำลังกรอก

### ผลที่วัดได้

เมนู **25 หน้า → 22 หน้า** · หมวด "ลูกค้าและการเงิน" **6 → 3**

## 9h. รวมหน้าที่สิทธิ์ไม่เท่ากัน — แท็บต้องเป็นด่าน ไม่ใช่ปุ่มที่ซ่อนไว้ (v1.12)

รอบนี้รวม **สต๊อกอะไหล่ + เบิก/ขายอะไหล่ + ของแถม** เป็นหน้า "อะไหล่และของแถม" หน้าเดียว
ต่างจากรอบ 9g ตรงที่สามหน้านี้**สิทธิ์ไม่เท่ากัน** จึงมีกับดักที่รอบก่อนไม่มี

| หน้าเดิม | ใครเข้าได้ |
|---|---|
| สต๊อกอะไหล่ | admin · manager · stock · tech · **acct** |
| เบิก / ขายอะไหล่ | admin · manager · stock · tech |
| ของแถม | admin · manager · stock · **sales** |

รวมหน้าแบบไม่คิด = บัญชีได้สิทธิ์เบิกของออกฟรี ๆ และเซลล์เห็นต้นทุนอะไหล่
**การรวมหน้าจึงห้ามรวมสิทธิ์** — สิทธิ์ยังคงเป็นของแต่ละแท็บเหมือนตอนเป็นคนละหน้า

### กฎ

**1 · ด่านอยู่ในตัวสลับแท็บ ไม่ใช่ที่การวาดปุ่ม**

```js
function ptTab(pane){
  const ok=PT_TABS.filter(t=>t.r.indexOf(ME.role)>=0);
  if(!ok.some(t=>t.p===pane)) pane=(ok[0]||{}).p||'pt1';   /* ← ด่านจริงอยู่บรรทัดนี้ */
  ...
}
```

ถ้าเช็กแค่ตอนวาดปุ่ม (`rParts()` วาดเฉพาะแท็บที่มีสิทธิ์) คนที่เปิด console แล้วเรียก
`ptTab('pt2')` เองจะเข้าได้ทันที — เหมือนกฎ 9b ที่ว่าด่านต้องอยู่ในฟังก์ชันที่*เขียน*ข้อมูล
ที่นี่คือฟังก์ชันที่*เปิด*แผ่น `ptTab()` เช็กซ้ำเองทุกครั้ง ไม่เชื่อว่าปุ่มถูกวาดมาถูกแล้ว

**2 · เหลือแท็บเดียวก็ไม่ต้องวาดแถบแท็บ**
บัญชีเห็นแค่ "สต๊อกอะไหล่" · เซลล์เห็นแค่ "ของแถม" — วาดแถบแท็บที่มีปุ่มเดียวคือเพิ่มของให้อ่านเปล่า ๆ
`rParts()` จึงวาดปุ่มก็ต่อเมื่อ `ok.length > 1`

**3 · ตัวเลขแดงบนเมนูรวมเป็นตัวเดียว**
เมนูเดียว = ตัวนับเดียว `PARTS` ที่ต่ำกว่าจุดสั่งซื้อ **บวก** `GIFTS` ที่ต่ำกว่าจุดสั่งซื้อ
(กฎเดียวกับที่รอบ 9g รวมตัวนับ 3 ตัวของหน้าดีล)

**4 · วาดทุกแผ่นที่มีสิทธิ์ตั้งแต่แรก อย่าวาดตอนกดแท็บ**
`rParts()` เรียก `rPartsStock()` / `rPartSale()` / `rGift()` ตามสิทธิ์รวดเดียว
`ptTab()` ทำแค่สลับคลาส `.on` — การสลับแท็บจึงไม่เรียก `render()` เลย และเป็นเหตุผลที่
`parts-r12.js` ตั้งเพดานไว้ว่าสลับแท็บ N ครั้งต้องเรียก `render()` ไม่เกิน N ครั้ง

### ผลที่วัดได้

เมนู **22 หน้า → 20 หน้า** · สิทธิ์ทั้ง 7 บทบาทเท่าเดิมทุกช่อง (ตรวจโดย `parts-r12.js`)

### ด่านตรวจ

| ชุด | ตรวจอะไร |
|---|---|
| `parts-r12.js` | 7 บทบาท — ปุ่มแท็บตรงสิทธิ์เดิมเป๊ะ · **เรียก `ptTab()` ตรง ๆ ด้วยแผ่นที่ไม่มีสิทธิ์ต้องไม่เปิดให้** · ทุกแผ่นที่มีสิทธิ์ต้องมีแถวจริง · สลับแท็บ 3 รอบไม่ล้นไม่ลูป · ตัวเลขแดง = อะไหล่ต่ำ + ของแถมต่ำ · เมนูเหลือ 20 และไม่มีหน้าเก่าค้าง |

พิสูจน์ด่านด้วยการถอดออก 3 แบบ — ถอด `if(!ok.some(...))` · ตัด `GIFTS` ออกจากตัวนับ ·
วาดปุ่มจาก `PT_TABS` แทน `ok` — **แดงทั้งสามแบบ**

## 9i. พิกัดเป็นหลักฐาน ไม่ใช่ตัวตัดสิน · เวลาต้องมาจากเซิร์ฟเวอร์ (v1.13)

เจ้าของสั่ง: *"ออกแบบหน่อยว่าจะทำยังไงให้พนักงานโกงเรื่องสถานที่ตอนเช็คอินไม่ได้
และ 3 สาขาหลัก สามารถเพิ่มโลเคชั่นได้เลย"*

### สิ่งที่ต้องยอมรับก่อน

ตราบใดที่พิกัดมาจาก `navigator.geolocation` **มันปลอมได้เสมอ** และเว็บมองไม่เห็นว่าปลอม
(`isFromMockProvider` เป็นของแอปเนทีฟ) นี่จึงเป็น **มาตรการทางวินัย ไม่ใช่มาตรการความปลอดภัย**
มันหยุดคนที่ลงเวลาจากบนเตียง ไม่หยุดคนที่ตั้งใจลงแอปปลอมตำแหน่ง — ต้องบอกเจ้าของตรง ๆ แบบนี้

**สิ่งเดียวที่ปลอมไม่ได้จริงคือเวลา** ถ้ามันมาจากนาฬิกาที่ผู้ใช้ตั้งเองไม่ได้

### กฎ

**1 · เวลาที่ใช้คิดเงินห้ามมาจากนาฬิกาของพนักงาน**

ของเดิม `punch()` ใช้ `hhmmss(new Date())` ตรง ๆ — หมุนนาฬิกาย้อนก็ "ไม่สาย" ฟรี ๆ
และตั้งเป็นวันอื่นก็ไปเขียนทับแถววันอื่นได้ **นี่เป็นรูที่ใหญ่กว่าเรื่องพิกัด** เพราะกระทบตัวเลขที่คิดเงินโดยตรง

```js
let SRV_SKEW=null;                 /* เวลาเซิร์ฟเวอร์ − เวลาเครื่อง (ms) */
const punchNow  = () => new Date(Date.now() + (SRV_SKEW||0));
const punchDate = () => iso(punchNow());
```

วัดส่วนต่างไว้ก่อน (จาก header `Date`) แล้วบวกกลับ — `punch()` จึงยังเป็นฟังก์ชันธรรมดา ไม่ต้อง `await`
และไม่ต้องแก้ผู้เรียกทุกจุดให้เป็น async **ทั้งเวลาและ "วันของแถว" มาจากตัวนี้ทั้งคู่**
นาฬิกาเครื่องยังถูกเก็บไว้เป็น `clientAt` + `skewMs` — ผลต่างคือหลักฐาน ไม่ใช่สิ่งที่ต้องซ่อน
ตอนต่อโหมดข้อมูลจริงให้ย้ายไปใช้ `now()` ของ Postgres ใน RPC `punch_clock()`

**2 · ผลการตัดสินต้องถูกแช่ไว้ ไม่คิดใหม่ตอนวาดจอ**

`geoVerdict()` ตัดสินตอนกดยืนยัน แล้วเก็บ `siteId` `siteName` `dist` `outside` ลงหลักฐานเลย
ถ้าปล่อยให้ `attFlags()` คำนวณระยะจาก `SITES` สด ๆ **วันที่เจ้าของขยับหมุดหรือขยายรัศมี
ธงของบันทึกย้อนหลังทุกใบจะเปลี่ยนเงียบ ๆ และเดือนที่ตรวจไปแล้วจะพลิกทั้งเดือน**
กติกาห้ามลบจุดกันได้แค่ชื่อ ไม่ได้กันเรขาคณิต — การแช่ผลไว้เท่านั้นที่กันได้

**3 · ยังไม่ได้ตั้งจุด = ปล่อยผ่าน ไม่ใช่ปิดกั้น**

วันที่ deploy ยังไม่มีใครปักหมุด ถ้าเส้นทางนี้ปิดกั้น **ทั้งบริษัทลงเวลาไม่ได้ในเช้าวันแรก**
สาขาที่ไม่มีจุด `active` → ข้ามการตรวจ ติดธง `nosite` ไว้เป็นข้อมูล และไม่เข้าคิวตรวจ

**4 · เปิดแบบสังเกตก่อน แล้วค่อยบังคับ**

`CFG.geoMode = 'watch'` เป็นค่าเริ่มต้น คิดและเก็บทุกอย่างแต่ยังไม่ติดธงและยังไม่บังคับ
iPhone ในตึกคอนกรีตรายงาน `acc` 65 ม. บ้าง 1500 ม. บ้าง **รัศมีที่เดาเอาจะเด้งใส่คนที่มาทำงานจริงทุกเช้า
แล้วสุดท้ายฟีเจอร์จะถูกสั่งปิด** ต้องเก็บตัวเลขจริง 2–3 สัปดาห์แล้วตั้งรัศมีจากหลักฐาน

**5 · ธงที่ขึ้นกับคนทำถูก คือธงที่ฆ่าธงอื่นทั้งหมด**

ถ้าคิวตรวจเต็มไปด้วยเรื่องที่ไม่ต้องทำอะไร ผู้จัดการจะเลิกอ่านคิว แล้วธงที่สำคัญจริงจะตายตามไปด้วย
`RV_SKIP` จึงกัน `lowacc` กับ `nosite` ไม่ให้ลากคนเข้ามาตรวจ และ `newdev` ไม่ติดธง
ถ้าคนนั้นยังไม่เคยมีประวัติเครื่องเลย (ไม่งั้นวันแรกทุกคนเข้าคิวพร้อมกัน)

**สองอย่างที่เจ้าของสั่งตัดออก และเหตุผลถูกต้อง**

| ตัด | เหตุผล |
|---|---|
| ยืนยันด้วยไอพี WiFi ร้าน | พนักงานบางคนใช้เน็ตมือถือ แยกไม่ออกระหว่าง "ไม่ได้ต่อ WiFi" กับ "ไม่ได้อยู่ที่ร้าน" |
| ธง "ลงเวลาห่างกัน 15 ม. ใน 90 วิ" | ร้านเล็ก คนยืนใกล้กันเป็นปกติ และเพื่อนเตือนกันแล้วลงพร้อมกันคือพฤติกรรมที่ถูกต้อง ไม่ใช่พิรุธ |

สิ่งที่ใส่แทนคือ **บรรทัดสรุปรายเดือนในแผ่นรายคน** ("ลงเวลาที่สำนักงานใหญ่ 18 ครั้ง · นอกพื้นที่ 3 ครั้ง เฉลี่ยห่าง 4.2 กม.")
คนโกงเป็นนิสัยเห็นเป็นรูปแบบชัดกว่าธงรายวัน และมันไม่กล่าวหาใคร

**6 · "ยืนยันก่อนเข้าเงินเดือน" = กันเงินไม่ให้ออก ไม่ใช่ตัดชั่วโมง**

ตัดชั่วโมงอัตโนมัติแปลว่าคนที่ออกไปทำงานจริงถูกหักเงินโดยไม่มีใครรู้
จึงกันที่ **ปุ่มส่งออกไฟล์โอนเงินและ CSV เงินเดือน** แทน — บังคับให้การตรวจเกิดขึ้นจริงโดยไม่แตะตัวเลขของใคร

**7 · ปล่อยทรัพยากรจากที่เดียว**

`geoStop()` อยู่ใน `closeModal()` ที่เดียวกับ `camStop()` ถ้าไล่ใส่ทีละทางออก
(ปุ่มปิด · Escape · แตะพื้นหลัง) จะมีทางที่ลืมเสมอ

### บทเรียนจาก mutation testing

เพดาน "ห่างเกินครึ่งชั่วโมงให้ข้าม" ของธง `jump` ดูสมเหตุสมผลตอนเขียน

## 9j. migration ที่ apply ผ่านไม่ได้แปลว่าใช้ได้ (v1.15)

รอบนี้ migration 12–14 ถูกรันลงฐานข้อมูลจริงเป็นครั้งแรก เจอสองอย่างที่
**ทั้งคู่มองไม่เห็นจากการอ่านโค้ด และหนึ่งในนั้นมองไม่เห็นแม้ apply สำเร็จ**

**1 · ชนิดข้อมูลของตารางตั้งค่า — ต้องเปิดดูก่อนเขียน insert**

```sql
insert into app_setting (key,value) values ('geo_mode','watch');
-- 22P02  invalid input syntax for type json · Token "watch" is invalid
```

`app_setting.value` เป็น `jsonb` ไม่ใช่ `text` · `'120'` ผ่านเพราะเป็น JSON number
แต่ `watch` เปล่า ๆ ไม่ใช่ JSON ที่ถูกต้อง ต้องเป็น `to_jsonb('watch'::text)` หรือ `'"watch"'`
migration 08 เขียนถูกอยู่แล้ว (`('work_start','"08:30"')`) — ตัวใหม่ต่างหากที่ลอกแบบผิด
**บทเรียน: ก่อนเขียน `insert` ลงตารางที่มีอยู่แล้ว ให้ query `information_schema.columns` ดูชนิดจริงก่อนเสมอ**

**2 · ฟังก์ชันที่เขียนข้อมูลต้องเป็น `volatile` — และข้อนี้ apply ผ่านฉลุย**

`pub.order_status` ประกาศเป็น `stable` แต่ตัวมันเอง `insert` ลงตารางนับการเรียกเพื่อจำกัดอัตรา
`create function` สำเร็จ · advisor เงียบ · `list_tables` เห็นครบ — **แต่ทุกครั้งที่เรียกจริงจะพัง**

```
0A000  INSERT is not allowed in a non-volatile function
```

เจอตอนยิง `curl` ผ่าน PostgREST เท่านั้น เพราะ Postgres ตรวจตอน**รัน** ไม่ใช่ตอน**สร้าง**

**กฎที่ได้: apply สำเร็จไม่ใช่เส้นชัย · ต้องยิงจริงทุก endpoint ที่เพิ่งสร้างด้วยสิทธิ์ของคนที่จะใช้จริง**
รอบนี้จึงไล่ยิงครบ — `anon` อ่าน 10 ตารางจริง (401 ทุกตัว) · อ่าน `pub.model` (200) ·
เขียน `pub.model` และเรียก `pub.gen_token()` (ปฏิเสธ) · embed จากวิวไปตารางแม่ 4 เส้นทาง (ตัน) ·
อัปไฟล์เข้า bucket (403) แต่อ่านสาธารณะได้ (404 ไม่ใช่ 401) · เพดาน 20 ครั้ง/ชม. ·
และเคสไฟแนนซ์ไม่ผ่านคืน `กรุณาติดต่อร้าน` โดยทั้ง payload ไม่มีคำว่า "ไม่ผ่าน" ไม่มีเหตุผล ไม่มีชื่อเจ้าไฟแนนซ์

ข้อสุดท้ายพิสูจน์ด้วยการ**สร้างการขายจริงชั่วคราวแล้วลบทิ้งในฟังก์ชันเดียวกัน**
(มี `exception` block ล้างให้ด้วยถ้าพัง) เพราะกฎเรื่องศักดิ์ศรีของลูกค้าต้องพิสูจน์ที่ SQL
ไม่ใช่แค่ที่ `publicshape-r14.js` — **ชั้นที่ลูกค้าเรียกจริงคือชั้นที่ต้องพิสูจน์**

**3 · ตัวอย่างในคู่มือก็ต้องมีด่านตรวจ ไม่งั้นมันคือโค้ดที่ไม่มีใครรัน**

ตัวอย่าง "เริ่มใน 5 นาที" ใน `docs/07-public-api.md` ที่เขียนไว้ให้คนทำเว็บคัดลอกไปวาง
**ใช้ไม่ได้จริง** — ทุกตัวอย่างในคู่มือลืมใส่ `Accept-Profile: pub` จึงยิงไปที่ `public.model`
ที่คนนอกแตะไม่ได้ ได้ `404` ทุกคำขอ คู่มือที่บอกว่า "คัดลอกไปวางแล้วได้เลย" จะพังตั้งแต่บรรทัดแรก

ชุด `qs-check` จึง**ดึงบล็อก HTML ออกจากตัวคู่มือตรง ๆ** (ไม่ได้เขียนใหม่) แล้วรันในเบราว์เซอร์จริง
ป้อนด้วย payload จริงที่ `curl` ดึงมา แล้วตรวจทั้งหัวข้อคำขอและสิ่งที่วาดออกมา
ถอด `Accept-Profile` ออกจากคู่มือ → แดง · ทำป้ายสต๊อกพัง → แดง
**คู่มือกับด่านตรวจผูกกันแล้ว แก้คู่มือให้ผิดเมื่อไหร่ก็รู้ทันที**

## 9k. กฎ "สีเน้นหนึ่งเดียว" ถูกยกเลิก — ระบบหลายสีผ่าน token (v1.20)

**เจ้าของยกเลิกกฎสีเดียวเอง 13 ส.ค. 2569** ในบรีฟแก้ไขครั้งที่ 1 (คำตอบ I1=ข):
เมนูใช้สีประจำกลุ่ม และแถบขั้นตอนเป็นสีเขียว กฎข้อ 1 เดิม (แดงยามาฮ่าจุดเดียวต่อจอ) จึงสิ้นสุด
สิ่งที่**ยังอยู่**คือกฎ "สถานะสื่อด้วยข้อความ+จุดสี ห้ามสีอย่างเดียว" — สีเพิ่มได้ แต่ห้ามให้สีทำงานลำพัง

กติกาของระบบสีใหม่:

- **ทุกสีคือ token** — `--grp1..--grp6` สีประจำ 6 กลุ่มเมนู (ผูกที่คลาส `g1..g6` ใน `buildNav`/แผ่นอื่น ๆ)
  ธีมมืดกำหนดชุดของมันเอง ห้ามเขียนสี hardcode ใหม่เหมือนเดิม
- **ขั้นตอน = เขียว** (`--pos` + `--pos-wash`): ขั้นที่ผ่านและขั้นปัจจุบันของ `steps()` เป็นเขียวทั้งคู่
  เขียว = เดินหน้า · **แดงเก็บไว้ให้ของที่ผิดจริง** (ตกราง `.pstep.off`, ค้างเกินเกณฑ์, เงินค้าง)
- **ธีมต่อคน (I3/I4/I6)**: `data-theme` บน `<html>` — `dark` / `warm` / `cool` เปลี่ยนเฉพาะ token
  เก็บใน `localStorage` คีย์ `famai_ui_<userId>` ต่อผู้ใช้ต่อเครื่อง ไม่ใช่ข้อมูลของร้าน จึงไม่ write-through
- **ขนาดอักษร 3 ระดับ (I2)**: `data-fs` ปรับชุด `--t-*` ทั้งแปดขนาดพร้อมกัน ไม่มีการปรับรายจุด
- **ฟอนต์ไทย 20 ตัว (I5)**: สลับที่ `--f-thai`/`--f-display` โหลดจาก Google Fonts ตอนเลือก
  ออฟไลน์ = ถอยกลับ Noto Sans Thai เงียบ ๆ ห้ามบล็อกแอป
- **เอกสารไม่ตามธีม**: `.doc` ล็อก token ภายในเป็นชุดกระดาษขาวเสมอ — ใบกำกับภาษีบนจอมืด
  ยังต้องดูเหมือนกระดาษที่กำลังจะพิมพ์ ไม่งั้นสิ่งที่เห็นก่อนพิมพ์กับที่พิมพ์ออกมาไม่ใช่ใบเดียวกัน

ด่านตรวจ: `theme-r20` — สลับธีมแล้ว token เปลี่ยนจริง, `.doc` ยังขาว, ตั้งค่าอยู่ต่อหลังรีโหลดเฉพาะคนเดิม,
เมนูมีครบ 6 กลุ่มสี, ขั้นตอนเป็นเขียว, 390px ไม่มีเลื่อนข้างทุกธีม

### สีกลุ่มเดินตามหน้า (v1.23)

เจ้าของสั่งเพิ่มว่า "แต่ละกลุ่มต้องมีสีเพื่อแยกกลุ่มให้ชัดกว่านี้" — v1.20 ทาสีไว้แค่ในเมนูซ้าย

  4.25-4.45 จึงเข้มขึ้นเป็น `#A05F0F` (สีเดิมใช้เป็นตัวอักษรบนพื้นกระดาษในเมนูอยู่แล้ว จึงอ่านยากมาแต่ต้น)

## 9l. ช่วงเวลาและการส่งออก (v1.24)

- **หน้าจอกับไฟล์ต้องเป็นชุดเดียวกัน** — ทุกหน้าที่มีแถบช่วง ต้องกรองรายการบนจอด้วย `inPer` ตัวเดียวกับที่
  ฟังก์ชันส่งออกใช้ · ห้ามมีลิสต์ที่ตัดจำนวนบนจอ (เช่น "15 รายการล่าสุด") แล้วส่งออกทั้งหมด —

  ถ้าเอาช่วง 30 วันย้อนหลังไปครอบจะได้ไฟล์เปล่า จึงส่งออกทั้งหมดตามขอบเขตสิทธิ์แทน

- **ด่านส่งออกอยู่ในฟังก์ชัน ไม่ใช่ที่ปุ่ม (§9b)** — `csvMoney` ตัดคอลัมน์เงินให้อัตโนมัติ ·

## 9m. หน้าแรกเบนโตะ — งานค้างนำ สต๊อกตาม (v1.25)

เจ้าของดูตัวอย่าง 6 แบบที่ `docs/dash/` แล้วสั่ง **"เอา 3 กับ 4 ผสมกัน"** —
แบบ 3 คือ "อะไรค้างอยู่" (วงแหวนความคืบหน้า + คิวงานตามวันครบกำหนด)
แบบ 4 คือ "สต๊อกทั้งเครือ" (โดนัทซ้อนวง + แท่งนอนหัวมน การ์ดเล็กแน่น)
เลือกเพิ่ม: **กริดเดียวทั้งหน้า งานค้างนำ · โทนเย็น · การ์ดเดิมต้องอยู่ครบ**
ตัวอย่างทั้ง 6 แบบยังเก็บไว้ที่ `docs/dash/` เป็นที่มาของดีไซน์

- **กริดเดียวจริง ๆ ไม่ใช่กริดซ้อนกริด** — `.bento` ใช้เฉพาะหน้าแรก · `#dKpis` เป็น `display:contents`
  ลูกของมันจึงเป็นช่องในกริดใบเดียวกับการ์ดอื่น การ์ดสองกลุ่มเลยเรียงคอลัมน์ตรงกัน
  **ห้ามแตะ `.g2`/`.g2e`** (อีก 20 หน้าจอใช้อยู่) และ **ห้ามแก้ `.kpi` ตรง ๆ** (อีก 6 หน้าจอใช้อยู่) —
  ทับได้เฉพาะแบบมีขอบเขต `.bento .kpi{...}`
- **ลำดับเรื่องคือลำดับสายตา** — ตัวเลขรวม → อะไรค้างอยู่ → สต๊อกทั้งเครือ → คนกับของ → รายการขาย
  "รอทะเบียน" กับ "ค้างจ่าย/ค้างรับ" ย้ายจากแถบ KPI ไปเป็นการ์ดวงแหวนของตัวเอง — ย้าย ไม่ใช่ตัดทิ้ง
- **สีกราฟเป็น token ชุด `--ch1..--ch6`** โทนน้ำเงิน-มิ้นต์ ประกาศที่ `:root` + ทับเฉพาะธีมมืด
  (ธีม `warm`/`cool` เปลี่ยนแค่กระดาษกับหมึก จึงรับชุดนี้ต่อได้เลย) ·
  **เกณฑ์คือ 3:1 ไม่ใช่ 4.5:1** เพราะเป็นพื้นของแท่ง/วง (วัตถุกราฟิก) ไม่ใช่ตัวอักษร ·
  วัดจริงในหน้าเว็บทั้ง 4 ธีม เทียบทั้ง `--card` และ `--paper` — สีที่ตาว่าโอเคมักไม่ผ่าน (เคยเจอกับ `--grp4`)
- **กราฟโค้งมนทุกตัวตามคำสั่งเจ้าของ** — `curvePath()` เบซิเยร์ลอดทุกจุดไม่มีมุมหัก (หนีบจุดคุมไม่ให้ทะลุกรอบ) ·
  `ringArc()`/`ringGauge()` วงแหวนปลายมน · แท่งเป็นแคปซูลด้วย `--r-pill` ·
  **ค่า 0 = ไม่มีแท่งเลย** ไม่ใช่เม็ดเล็ก ๆ (เม็ดจะอ่านเหมือนมีของ) แต่ค่า > 0 ดันกว้างอย่างน้อยเท่าความสูงราง
- **แบ่งช่วงกราฟยอดขายสูงสุด 12 ช่วง** (`min(12, จำนวนวัน)`) — หยาบกว่านี้ยอดเฉลี่ยเท่ากันทุกช่วง
  เส้นแบนราบไม่บอกอะไร · ช่วงเลือกเป็นวันเดียวจะไม่มีเส้น ให้ขึ้นตัวเลขตรง ๆ แทน ดีกว่าลากเส้นจากจุดเดียว
- **ตัวเลขทุกตัวมาจาก `dSales()` / `dUnits()`** ชุดเดียวกับ KPI ที่อยู่เหนือมัน กราฟกับตัวเลขจึงตรงกันเสมอ
  ห้ามคิดจาก `SALES`/`UNITS` ตรง ๆ (ของเดิมเคยบวกเลขปลอมให้กราฟดูมีข้อมูล ผลคือกราฟขัดกับ KPI ตัวเอง)
- **สีไม่ใช่ตัวสื่อความหมายเดี่ยว (กฎข้อ 3)** — ทุกส่วนของโดนัทมีชื่อรุ่นกับจำนวนใน legend ·
  คิวงานที่เลยกำหนดขึ้นข้อความ "เลย N วัน" ไม่ใช่แค่จุดแดง · ช่วงอายุรถที่เกินเกณฑ์มีคำกำกับ

ด่านตรวจ: `dash-r25` (8 ข้อ) — การ์ดเดิมครบ 12 ใบ · กราฟโค้งจริงทั้งเส้น/วง/แท่ง ·
เลขบนการ์ดเท่ากับ `dUnits()`/`dSales()` และขยับตามช่วงเวลาและสาขา · ตัวเลขกลางวงแหวนตรงกับส่วนโค้ง
และคำนวณจากระเบียนจริง · คิวเรียงตามวันครบกำหนด · คนไม่มีสิทธิ์ `money` เห็น `—` · 390px ไม่ล้น ·
คอนทราสต์ `--ch1..6` ครบ 4 ธีม — **พิสูจน์ครบทั้ง 12 จุดว่าถอด guard ออกแล้วแดงจริง**

- ทำไมต้องเขียน state ทันที ไม่ staging: ด่าน `brief-r11` ยิง `.value` ใส่ `[data-pf]` แล้วเรียก `.onchange()`
  ตรง ๆ จากนั้นอ่าน `dPeriod()` ทันที · `navper-r26` กดชิปแล้วอ่าน `dSales()` ทันที

### §9p · เส้นทางดีลเรียงตามงานจริง ไม่ใช่ตามลำดับของข้อมูล (v1.28)

**คำสั่งเจ้าของ:** `คุยกับลูกค้า → ไฟแนนซ์ → เปิดการขาย → ส่งมอบ → ทะเบียนรถ`
เพราะลูกค้าต้องยื่นไฟแนนซ์ผ่านก่อน ร้านถึงเปิดการขายได้ · ส่งมอบแล้วลูกค้าใช้**ป้ายชั่วคราว**
ระหว่างรอทะเบียนจริงจากขนส่ง · ดูแลหลังส่งมอบเป็นหน้าที่ฝ่ายบริการ

**ของเดิมเรียงกลับด้านสองจุด** และคอมเมนต์ในโค้ดยอมรับไว้ตรง ๆ ว่าเลือกเรียงตาม
"ลำดับของข้อมูล" (ใบขายเกิดก่อน เคสสินเชื่อสร้างจากใบขาย) ไม่ใช่ลำดับของงาน
— **บทเรียน: ลำดับบนจอต้องเล่าเรื่องของผู้ใช้ ไม่ใช่เล่าโครงสร้างตาราง**
ถ้าข้อมูลเรียงไม่ตรงกับงาน ให้ตีความข้อมูลใหม่ อย่าบิดงานให้เข้ากับข้อมูล

**วิธีแก้โดยไม่แตะฐานข้อมูล** — ใบขายที่ไฟแนนซ์ยังไม่ผ่านอ่านว่าเป็น **"ใบจอง"**
ขั้น "เปิดการขาย" จึงติ๊กเมื่อไฟแนนซ์อนุมัติ (เงินสดติ๊กทันที) · เป็น**หมุดหมาย ไม่ใช่ที่พัก**
ที่พักจริงมีสี่ตัว: `lead` `fin` `deliver` `plate` — ทั้งหมดคำนวณจาก SALES/FINCASES/REGS ตามกฎ §9g

**"จบงาน" กับ "แถบเต็ม" เป็นคนละคำถาม** (จุดที่ตัดสินใจยากที่สุดของรอบนี้)
เจ้าของเลือกว่าดีล **จบตอนส่งมอบ** ทะเบียนเป็นงานต่อท้าย ถ้าทำตามตัวอักษรคือแถบเต็มตั้งแต่ส่งมอบ
แต่นั่นแปลว่าติ๊กขั้นที่ยังไม่เกิดขึ้นจริง = โกหกบนจอ ขัดกฎข้อ 9 จึงแยกเป็นสองค่า:
- `d.delivered` → ใช้ตอบว่า "สำเร็จหรือยัง" (% หน้าแรก · หน้าสาธารณะ · ส่งต่อฝ่ายบริการ · KPI ดีลที่ยังไม่จบ)
- `d.i` → ตำแหน่งบนแถบ ขั้นทะเบียนยังเดินอยู่จนป้ายจริงมา
หน้าจอจึงขึ้นว่า **"ส่งมอบแล้ว จบงานขาย · รอทะเบียนจริงจากขนส่ง"** — สำเร็จแล้วแต่ยังมีงานธุรการค้าง

**ผลที่ตามมาซึ่งพลาดง่าย** — เดิม `r.stage !== 'ส่งมอบแล้ว'` แปลว่า "ยังไม่จบ" ได้ทุกความหมาย
เพราะส่งมอบเป็นขั้นสุดท้าย พอส่งมอบขยับมากลางเส้นทาง คำถามนั้นแตกเป็นสอง ต้องเลือกให้ตรงทีละที่:
`regDone(r)` = ลูกค้าได้รถแล้วหรือยัง · `regPlated(r)` = งานทะเบียนจบจริงหรือยัง
เขียนเป็นฟังก์ชันสองตัวไว้ที่เดียว ดีกว่าปล่อยให้แต่ละหน้าเทียบชื่อขั้นเอง

**กับดักตอนเขียนด่าน** — ลูปที่เดินขั้นด้วย `while (stage !== 'ส่งมอบแล้ว')` กลายเป็นลูปไม่รู้จบ
ทันทีที่ mutation สลับลำดับขั้น (regAdvance คืน false ตลอด) ทำให้ด่าน timeout แทนที่จะแดง —
ลูปที่เดิน state machine ในด่านต้องมีตัวนับกำกับเสมอ · และ `indexOf('ไฟแนนซ์')` ในผังกระบวนการ
ไปเจอ "เสนอราคา + เทียบไฟแนนซ์" ก่อน ทำให้ mutation ไม่แดง ต้องจับชื่อขั้นแบบเต็มคำ

ด่านตรวจ v1.28: `flow-r28` (8 ข้อ · mutation 8 ตัว) + แพตช์ `deal-r10` `steps-r10` `care-r17` `loop-r10`

แล้วจะมีสาขาให้เลือกและสามารถบันทึกได้ หรือกดแค่บริษัทก็บันทึกได้เช่นกัน"*

และตั้งชื่อสาขาเป็นชื่อบริษัท ตัวเลือกจึงอ่านเป็นรายชื่อบริษัท ทั้งที่ค่าเป็นรหัสสาขา
**ชั้นบริษัทไม่เคยโผล่บนตัวกรองเลย** — บทเรียน: ข้อมูลสาธิตที่แบนเกินจริงซ่อนช่องว่างของ UI ไว้ได้นาน

**ค่าเดียวบอกสามระดับ** — `''` ทุกสาขาที่เห็นได้ · `'CO2'` ทุกสาขาของบริษัทนั้น · `'FMM01'` สาขาเดียว
รหัสบริษัทขึ้นต้น `CO` เสมอ รหัสสาขาไม่เคย จึงแยกกันได้**โดยไม่ต้องเก็บฟิลด์ที่สอง** (กฎ §9g)
การเทียบรวมไว้ที่ `brMatch(sel, code)` ที่เดียว — ของเดิมเขียน `(!br || x.branch===br)` กระจายอยู่ห้าที่
ชื่อที่เอาไปขึ้นป้าย/หัวกระดาษใช้ `scopeName(sel)` ตัวเดียวกันหมด

**"กดบริษัทก็บันทึกได้" กับ "เลือกสาขาต่อ" เป็นทางเดียวกัน** — กดบริษัท = เลือกระดับบริษัท**ทันที**
แล้วกางสาขาต่อข้างล่างโดยแผงยังเปิดอยู่ · ไม่มีปุ่ม "ใช้ทั้งบริษัท" แยกต่างหาก
ผู้ใช้จะได้ไม่ต้องเลือกว่าจะกดปุ่มไหน (§9g "งานหนึ่งชิ้นจบในหน้าเดียว")

**`#navBrSel` ยังอยู่เป็นตัวเก็บค่า** แค่ซ่อนเชิงภาพ — แผงเขียน `.value` แล้วเรียก `.onchange()` เดิม
กลไกเดียวกับช่องวันที่ที่ซ่อนหลัง `#perCal` (v1.27) ทางเดินและด่านที่ยิงตรงจึงไม่ต้องแก้เลย
และแผงเป็น `position:fixed` จึงไม่นับชั้นกล่องและไม่ดัน `scrollWidth` ที่ 390

**ตัวกรองสาขาในหน้าถูกซ่อนทั้งห้าตัว** ตามคำสั่ง "ให้มีที่เดียว" — ตามด้วยการถอดแถวสาขา
ออกจาก `FILTERS` ของแผ่นตัวกรองมือถือด้วย เพราะแผ่น**ยืม element ตัวจริง** ถ้าซ่อนไว้เฉย ๆ จะได้แถวเปล่า
หน้าเข้างานที่มีตัวกรองเดียวคือสาขา จึงไม่มีแผ่นแล้ว — `fsSync()` ต้องทนหน้าที่ไม่มี config

**กับดักที่เจอ**
- **จังหวะกระจายข้อมูลสาธิตต้องไม่ชนกับจังหวะที่ข้อมูลอื่นหยิบไปใช้** — รอบแรกกระจายสาขาด้วย
  `u.branch = g[i % 3]` แต่ผู้ซื้อสาธิตหยิบรถทุก ๆ 3 คัน (`sellable[i*3 % n]`) รถที่ถูกขาย
  จึงตกสาขาเดียวทั้งหมด: สาขาใหม่มีรถ 10 คันแต่**ลูกค้า 0 ราย** เซลล์ที่ประจำสาขานั้นเปิดหน้าดีลมาเจอจอเปล่า
  (`deal-r10` ค้างจน timeout · `search-r26 [5]` หาลูกค้าในขอบเขตไม่เจอ) แก้ด้วย `g[⌊i/3⌋ % 3]`
  ให้คาบของสาขา (3) ไม่หารลงตัวกับก้าวของผู้ซื้อ · **บทเรียน: ข้อมูลสาธิตที่กระจายด้วย modulo
  ต้องดูก่อนว่ามีใครหยิบด้วย stride เดียวกันอยู่ไหม แล้วนับผลจริงต่อสาขา อย่าเชื่อว่าโค้ดกระจายแล้วมันกระจาย**
- ป้ายเดียวกันเคยมีสามสำนวน: `navLbl()` อ่านข้อความใน `<option>` ("ทุกสาขาของ X") ·
  `navBrText()` ก็อ่าน `<option>` เหมือนกัน · ส่วนที่อื่นใช้ `scopeName()` ("X · ทุกสาขา")
  ตอนนี้ทั้งป้ายปุ่มและข้อความ "ยังไม่ได้ใช้" เรียก `scopeName()` ตัวเดียว และ `navBrText()` ถูกลบทิ้ง
- ปุ่มเปิดแผงเป็น **toggle** — ด่านที่กดเปิดซ้ำโดยไม่ปิดก่อนจะกลายเป็นสั่งปิด แล้ว timeout
  แทนที่จะแดง · ในด่านต้อง `brPickClose()` ให้แน่ก่อนเปิดทุกครั้ง
- กดปุ่มยืนยันที่ `disabled` = Playwright รอจนหมดเวลา ไม่ใช่ fail — ต้องเช็ค `.disabled` ก่อนคลิกเสมอ
- จอคอมไม่มีแผ่นมือถือ `navCtlClose()` จึงคืนค่าตั้งแต่บรรทัดแรก — ปิดแผงต้องสั่งตรงใน `#navOk`

ด่านตรวจ v1.29: `brpick-r29` (8 ข้อ · mutation 7 ตัว) + แพตช์ `fsheet-r3` (เปลี่ยนตัวอย่างเป็น `rpDim`
ซึ่งมีเฉพาะแท็บขายรายเดือน) · `navok-r27` (ป้ายระดับบริษัทมีคำว่า "ทุกสาขา" อยู่ในตัว ต้องเทียบให้ตรงตัว)

### §9r · แถบขั้นตอนโตขึ้นบนจอคอม · ดอกจันแดงบนช่องที่จำเป็น (v1.30)

**คำสั่งเจ้าของ (23 ส.ค. 2569):** *"บนคอม ส่วนของ process bar ที่เป็นสีเขียว อยากให้ทำให้ใหญ่ขึ้น
เพื่อที่จะดูได้ชัด"* และ *"ในทุกฟอร์มที่ต้องกรอกข้อมูล อยากให้โชว์ด้วยว่าช่องไหนจำเป็นต้องกรอก
โดยใช้ดอกจันทร์สีแดง"*

#### ① แถบขั้นตอนขยายเฉพาะจอคอม

`.pstep` **ไม่เคยมี media query เลยสักอัน** มาก่อน — ขนาดที่ออกแบบให้พอดีจอ 390px
ถูกใช้ซ้ำบนจอ 1440px ที่มีที่ว่างเหลืออีกเท่าตัว วงเลยดูเป็นจุดเล็ก ๆ แทนที่จะเป็นแถบที่อ่านจากระยะที่นั่งได้

| | ≤900px | ≥901px |
|---|---|---|
| วงไอคอน `.pn` | 28px | **40px** |
| ไอคอนใน วง | 16px | **22px** |
| วงแหวนขั้นปัจจุบัน | 4px | **6px** |
| เส้นเชื่อม `.pl` | สูง 3px | **สูง 5px** |
| ชื่อขั้น `em` / วันที่ `.pdt` | 11 / 10px | **13 / 11.5px** |
| ความกว้างสูงสุดของชื่อขั้น | 88px | **120px** |

**เกณฑ์ 901px ไม่ใช่ค่าที่คิดขึ้นใหม่** — เป็นเส้นเดียวกับที่แอปสลับ nav เป็นแบบจอคอมอยู่แล้ว
(`@media (max-width:900px)`) โปรเจกต์นี้มีนิยาม "จอคอม" เส้นเดียว ไม่ใช่สองเส้น
นี่เป็น `min-width` ก้อนแรกของไฟล์ — ที่เหลือเป็น `max-width` ทั้งหมด

**min-width ของเส้นเชื่อมจงใจไม่ขยาย** (คงไว้ 10px) — ค่านั้นมีผลเฉพาะตอนตารางแคบ
ถ้าดันเป็น 14px ด้วย คอลัมน์ความคืบหน้าในตารางดีลจะกว้างจาก 240 เป็น 256px
แล้ว `.tw` จะเริ่มเลื่อนข้างตั้งแต่จอ 1024px แทนที่จะพอดีเป๊ะ (วัดแล้ว: 712 = 712)
ช่วง 901–1023px ตารางดีลเลื่อนข้างอยู่แล้วตั้งแต่ก่อนแก้ (650 > 589 ที่ 901px) — ของเดิม ไม่ใช่ของใหม่

**ห้ามใส่พื้น/มุมโค้ง/ระยะขอบข้างให้ `.pstep` หรือ `.pst`** ตอนขยาย — จะกลายเป็นกล่องชั้นที่ 3
แล้ว `boxdepth` แดงทุกบทบาท (กฎข้อ 1) ขยายได้แค่ตัวเลขขนาดของสิ่งที่มีอยู่แล้ว

`steps-r10.js` ผูกค่าไว้ที่ `const PN = W >= 901 ? 40 : 28` ที่เดียว และตรวจทั้งแถบในตารางและในหน้ารายละเอียด
— ถอด media query ออก 1440px แดง 17 ข้อทันที (พิสูจน์แล้ว)

#### ② ดอกจันแดง = เว้นว่างแล้วบันทึกไม่ผ่าน

**ดอกจันเป็นป้ายบอกทาง ไม่ใช่ด่าน** ด่านจริงยังอยู่ในฟังก์ชันเขียนข้อมูลทุกตัวเหมือนเดิม (§9b)
สิ่งที่เพิ่มคือ `REQ` — **รายชื่อช่องที่จำเป็นทั้งแอป 49 ช่อง ประกาศที่เดียว** และ `markReq()`
ที่แปะ `<span class="rq">*</span>` เข้า `label.fl` ของช่องนั้น เรียกจาก 3 จุด:
`openModal()` (ป๊อปอัปทุกตัวผ่านทางนี้ทางเดียว) · ท้าย `render()` (วาดหน้าใหม่แล้วต้องยังอยู่) ·
และตอนบูตหนึ่งครั้ง (หน้าล็อกอินบัญชีจริงก็เป็นฟอร์ม)

**ทำไมเป็นรายการเดียว ไม่ใช่แก้ป้ายทีละ 49 จุด** — คำถาม "ช่องไหนบังคับบ้าง" ต้องมีคำตอบอยู่ที่เดียว
ที่อ่านแล้วจบ และด่านตรวจต้องอ่านรายการเดียวกันนั้นได้ ไม่ต้องเดาจากมาร์กอัป

**ช่องที่จงใจไม่มีดอกจัน** (เขียนไว้ในคอมเมนต์เหนือ `REQ` ด้วย)
- **บังคับบางกรณี 4 ช่อง** — `wsDest` (ผู้ซื้อเป็นบริษัทในเครือ) · `psWhy` (ลงเวลานอกจุด) ·
  `psNote` (กดปุ่มติดปัญหา) · `rjWith` (เหตุผล = ติดไฟแนนซ์เจ้าอื่น) → เขียนเงื่อนไขไว้ในป้ายแทน
  **ดอกจันถาวรบนช่องที่บางทีไม่ต้องกรอก จะสอนให้คนเลิกเชื่อดอกจันทั้งแอป**
- `svSearch` (ช่องค้นหา) · `sUnit` (ด่านคือ "ไม่มีรถว่างให้ขาย" ไม่ใช่ "ลืมเลือก")
- ช่องที่ล็อกอยู่ (`disabled`) — ไม่สั่งให้คนกรอกของที่แตะไม่ได้

**สองช่องที่ไม่มี `label` ให้แปะ** — `#dlPlate` (เลขทะเบียน อยู่ในแถวปุ่ม) และช่องราคาต่อคัน
ในตะกร้าขายส่ง (`data-wci` เป็นแถวซ้ำที่สร้างจาก JS) ทั้งคู่บังคับจริง จึงฝังดอกจันไว้หน้าช่องในมาร์กอัปเลย
และ `required-r30` ทำเครื่องหมาย `inline:1` ไว้เพื่อไม่ให้ถูกนับว่าเป็น "ดอกจันเกิน"

**ป้ายที่เขียน "(จำเป็น)" ไว้เองถูกถอด 2 จุด** (`#fxWhy` `#cdDetail`) — ดอกจันบอกแล้ว เขียนซ้ำเป็นเสียงรบกวน
ส่วนป้ายที่เขียน "(ไม่บังคับ)" ยังอยู่ทั้ง 3 จุด เพราะเป็นข้อมูลคนละอย่าง (บอกว่า *ไม่* ต้องกรอก)

**คอนทราสต์** `--accent` บนพื้นการ์ดได้ 4.80 (ธีมสว่าง) และ 4.73 (ธีมมืด — `--accent` พลิกเป็น `#FF3B47`
บน `--card` `#1C1E25`) ผ่าน 4.5 ทั้งคู่ · และตัวอักษร `*` เองสื่อความหมายได้โดยไม่พึ่งสี ตรงกฎข้อ 3

**ด่านตรวจ `required-r30.js` — 50 เคส ตรวจสองทางในรอบเดียวต่อช่อง**
1. ดอกจันโผล่จริง อยู่ในป้ายของช่องนั้น เป็นตัวอักษร `*` กว้างไม่เป็น 0 และเป็นสี `--accent`
2. **เคลียร์ช่องนั้นแล้วยิงฟังก์ชันบันทึกจริง ต้องได้ toast แดงที่ข้อความตรงกับด่านของช่องนั้น**
   ไม่ใช่ "แดงก็พอ" — ถ้าเด้งด่านอื่นแปลว่าเคสตั้งไม่ตรง และเรายังไม่ได้พิสูจน์ด่านของช่องนี้
3. ไม่มีดอกจันเกินบนช่องที่ไม่ได้อยู่ใน `REQ` (ดอกจันเกิน = โกหกอีกแบบ)
4. ทุกชื่อใน `REQ` ต้องมีเคสในไฟล์ — เพิ่มชื่อแล้วไม่เขียนเคส ด่านแดง
ผลรัน: **พิสูจน์ด่านจริงครบ 50/50 ช่อง** · mutation: ถอด `markReq()` → แดง 49 ข้อ ·
ถอด `if(!name)` ใน `saveSale` → แดงเฉพาะ `sCust` ข้อเดียว

**กับดักที่เจอตอนเขียนด่านนี้**
- **เคลียร์ช่องแล้วยิง `change` = ช่องกลับมามีค่าเอง** — `rWsSale()` วาด `#wsPartner` ใหม่ทั้งก้อน
  แล้วเลือกตัวแรกให้ · แท็บค่างวดคิด `#fNet` ใหม่ · ด่านจึงไม่มีวันเด้ง ตอนแรกอ่านผลผิดว่า "ด่านไม่ทำงาน"
  สิ่งที่ตรวจคือ "ตอนกดบันทึก ช่องนี้ว่าง" ไม่ใช่เส้นทางที่ผู้ใช้พิมพ์จนว่าง → เคลียร์แบบเงียบ ไม่ยิง event
- **ช่องที่มีด่านเรียงกันหลายชั้นต้องเติมช่องก่อนหน้าให้ถูกก่อน** ไม่งั้นจะจับได้แต่ด่านตัวแรกเสมอ
  (เช่น `eStaff` ต้องมี `eAmt` + `eCat` ก่อน · `obCode` ต้องมี `obName` ก่อน)
- **`page.goto` รอ `load` ในกล่องที่ออกเน็ตไม่ได้ = รอคำขอ Google Fonts จนหมดเวลา**
  49 เคส × การรอ = รันครึ่งชั่วโมง · ใช้ `domcontentloaded` แล้วรอ `typeof REQ !== 'undefined'` แทน
  (สคริปต์ของแอปอยู่ในไฟล์เดียว รันจบตั้งแต่ parse อยู่แล้ว)
- **ตั้ง `ctx.setDefaultTimeout` ให้สั้น** เส้นทางเคสที่พังจะแดงใน 4 วิ ไม่ใช่ 30 วิต่อเคส

### §9s · หนึ่งสี = หนึ่งการ์ด · รูปผูกกับสี ไม่ใช่รุ่น (v1.31)

**คำสั่งเจ้าของ (23 ส.ค. 2569):** *"ตอนเพิ่มรุ่นในตั้งค่าระบบ อยากให้แยก 1 สีในแต่ละรุ่นเป็น 1 card
เพราะว่าตอนใส่รูป ต้องใส่รูปรถให้ตรงสี พอเป็นให้เพิ่มรูปได้รูปเดียว แต่ใส่สีได้หลายบรรทัด จะทำให้สับสนได้"*

**ของเดิมสับสนเพราะโครงข้อมูลสับสน** — `PRICE[รุ่น]` มีรูปได้ใบเดียว (`img`/`imgUrl`) แต่มีสีได้หลายสี
(`c:{'010A':'ดำ','010B':'แดง'}`) แปลว่า NMAX 4 สีใช้รูปใบเดียวกันหมด ลูกค้าเปิดดูก็เห็นรถผิดสี
หน้าจอสับสนเพราะข้อมูลสับสนก่อน — แก้ที่หน้าจออย่างเดียวไม่พอ

**โครงใหม่: สีคือของหนึ่งชิ้น ไม่ใช่ข้อความ**

```js
c:{ '010A':{ name:'ดำ', img?, imgUrl?, imgFullUrl? } }   // คีย์ = รหัสสียามาฮ่า
```

รูปอยู่ในสี **ไม่มีรูประดับรุ่นเหลืออยู่เลย** — จงใจไม่เก็บรูปรุ่นไว้เป็นตัวสำรอง เพราะ
"รูปรุ่นกับรูปสี อันไหนชนะ" คือความสับสนแบบเดิมในร่างใหม่ · สีที่ยังไม่มีรูปได้เงารถที่ระบายด้วยสีจริงของมัน
ซึ่งเป็นคำตอบที่ถูกอยู่แล้วและบอกได้ด้วยตาว่า "ยังขาดรูปสีนี้"

**`bikeArt(รุ่น, ชื่อสี, รหัสสี)` — เพิ่มอาร์กิวเมนต์ที่สาม** ทั้ง 6 จุดที่เรียกมี `u` อยู่ในมืออยู่แล้ว
จึงส่ง `u.colorCode` ต่อได้ทันที · หาสีจาก**รหัส**ก่อนเสมอ ค่อยตกไปเทียบชื่อ —
เพราะรุ่นเดียวมีชื่อสีซ้ำได้จริง (`BJKD00` มีทั้ง `'ฟ้า'` และ `'ฟ้า/ดำ'`) การเทียบด้วยชื่ออย่างเดียวจะหยิบผิดใบ

**หน้าจอ 3 ที่ที่เปลี่ยน**
1. **แผ่นเพิ่ม/แก้รุ่น** — `textarea` "บรรทัดละสี" หายไป กลายเป็นการ์ดต่อสี:
   รูปตัวอย่าง + รหัสสี + ชื่อสี + ปุ่มเลือกรูป + ปุ่มเอาออก · ปุ่ม "+ เพิ่มสี" ข้างล่าง
   การ์ดแยกด้วย**เส้นคั่น**อย่างเดียว ไม่มีพื้น ไม่มีมุมโค้ง ไม่มีระยะขอบข้าง จึงไม่บวกชั้นกล่อง (กฎข้อ 1)
2. **รายการรุ่น** — คอลัมน์ "รูป" กับ "สี" ยุบเป็น **"สีและรูป"** คอลัมน์เดียว
   สีละช่อง รูปของสีนั้นเอง + จุดสี + ชื่อ + รหัส · สีที่ไม่มีรูปเขียนกำกับว่า "ยังไม่มีรูป"
   (สถานะ = ข้อความ + จุดสี ไม่ใช่สีล้วน ตามกฎข้อ 3) — **เจ้าของเลือก "รุ่นละแถว โชว์รูปทุกสีเรียงกัน"**
3. **เพย์โหลดสาธารณะ** — `colors[]` มี `photo`/`photoFull` ต่อสี · คีย์บนสุดยังเป็น 11 ตัวเดิมเป๊ะ
   (`publicshape-r14` ล็อกไว้) · `photo` ระดับรุ่นกลายเป็น "รูปของสีแรกที่มีรูป" เพื่อไม่ให้ผู้ใช้เดิมพัง

**ช่องเลือกไฟล์มีตัวเดียวใช้ร่วมทุกการ์ด** — ถ้าทำ `<input type="file">` ต่อการ์ด `id` จะซ้ำทันทีที่มี 2 สี
ปุ่มในการ์ดจำว่า "ใบไหนกำลังรอไฟล์" แล้วสั่ง `.click()` ช่องกลางตัวเดียว

**วาดรายการใหม่เฉพาะตอนเพิ่ม/ลบ/เปลี่ยนรูป ไม่วาดตอนพิมพ์** — ค่าที่พิมพ์เก็บเข้า `rows` ทาง `oninput`
ถ้าวาดใหม่ทุกตัวอักษร เคอร์เซอร์จะหลุดทุกครั้ง

### §9u · แผงรายชื่อรุ่นใต้ช่องค้นหารถ (v1.40)

เจ้าของ (25 ส.ค. 2569): "หน้าขายรถ ส่วนรายละเอียดการขาย ช่อง search อยากให้พอกดช่องนั้น
จะมีรายชื่อรุ่นขึ้นมาให้กดครับ" — ช่อง `#svQ` เดิมต้องพิมพ์เลขเครื่อง/เลขถัง ≥3 ตัวถึงจะมีอะไรเกิด
คนที่ยังไม่รู้เลขอะไรเลย (เคสที่พบบ่อยสุด: ลูกค้าชี้รุ่นจากหน้าร้าน) ไม่มีทางเข้า

**ทางที่เลือก + เหตุผล**

- ทำที่โค้ดกลาง `vehCascadeWire`/`vehCascadeFill` ไม่ใช่ที่หน้าขาย — หน้าจอง (`#bkQ`) ใช้ wire
  ตัวเดียวกันจึงได้แผงฟรีทั้งสองหน้า และกติกา pool ของใครของมัน (sellPool/bookPool) ตามเดิม
- แผงใช้ `.sug`/`.si` เดิมของ autocomplete ลูกค้าทั้งชุด — ไม่มี CSS ใหม่แม้แต่บรรทัดเดียว
  แถวสูง ≥44px ผ่านเกณฑ์เป้าแตะ และ boxdepth ไม่นับเพราะเนื้อหาอยู่ใน `.si` (อยู่ในลิสต์ CONTENT)
- **แผงไม่มี state แยก** (กฎข้อ 8) — วาดจาก `pool()` สดทุกครั้ง และ**ปิดรวมศูนย์ที่บรรทัดแรกของ
  `vehCascadeFill`** ซึ่งถูกเรียกจากทุก render → back-fill เจอคัน / กดเลือกรุ่น / `sUnitSet` /
  refreshAll / กลับเข้าหน้า ล้วนปิดแผงเองโดยไม่ต้องไล่ปิดรายจุด · จุดนี้สำคัญกับด่านเดิม:
  picker-r33 ตั้ง `.value` ตรง ๆ แล้วเรียก `rSell()` โดยไม่ยิง event — state แยกจะค้างข้ามเคสทันที
- back-fill เดิม (เลขเครื่อง/เลขถัง/รหัสรุ่น ≥3 ตัว) **ชนะการกรองชื่อรุ่นเสมอ** — กิ่ง hit
  `return` ก่อนถึง `sugDraw()` · การพิมพ์ชื่อรุ่น (ซึ่ง back-fill ไม่ค้นตั้งแต่แรก) จึงเป็นแค่
  ตัวกรองรายชื่อในแผง ไม่แตะสัญญาเดิมแม้แต่บิตเดียว

**กับดักที่เจอตอนเขียนด่าน (modelsug-r40 — 8 ข้อ · mutation 9 ตัว)**

- ลำดับใน `oninput` ต้อง `redraw()` ก่อน `sugDraw()` — สลับเมื่อไหร่ fill จะปิดแผงทับที่เพิ่งวาด
- แถวแผงต้องใช้ `onmousedown`+`preventDefault()` ไม่ใช่ `onclick` — blur ของ input ยิงก่อน click
  แผงถูกซ่อนแล้วคลิกไม่ติด (บทเรียนเดิมของ `#sCust` ที่ :5073)
- mutation ที่แพตเทิร์นเป็นสตริง JS ต่อกัน (`+'...'`) ต้อง match ถึงตัวปิดสตริงจริงในซอร์ส
  ไม่ใช่ตัดที่ใจอยากตัด — `' คัน</span>'` ไม่มีในไฟล์ มีแต่ `' คัน</span></button>'`
- แบตเตอรี mutation ต้องมี**สำเนาเขียวหลังแก้จริง**ไว้คืนไฟล์ (ไม่ใช่ .bak ก่อนแก้) และเทียบ md5
  ทุกรอบ — รอบนี้พลาดจุดนี้หนึ่งครั้ง mutation สองตัวซ้อนกันในไฟล์ ต้องไล่คืนทีละบรรทัด
