# ส่งงานหนึ่งรอบ

Vercel ผูกกับ `claude/start-b18xi3` — **push = ขึ้นจริงทันที** ไม่มีขั้น staging
ลำดับนี้คือด่านที่กันของพังไม่ให้ถึงหน้าร้าน ข้ามข้อไหนก็เสียของที่ข้อนั้นกันไว้

## 1 · แยกคำสั่งเป็นข้อ แล้วถามเฉพาะที่เปลี่ยนรูปงาน

เจ้าของสั่งเป็นย่อหน้ายาว มักมี 2-5 เรื่องปนกัน — แยกให้ครบก่อน ตกข้อไหนคือส่งงานไม่ครบ

ใช้ `AskUserQuestion` เฉพาะคำถามที่**คำตอบต่างกันแล้วงานคนละรูป** (จอคอมกี่เดือน · หน้าที่ไม่มีตัวกรอง
จะเอาปุ่มด้วยไหม) · เรื่องที่มีค่าปริยายชัดให้ตัดสินเองแล้วบอกในรายงาน
เจ้าของตอบสั้นและเลือกตัวที่แนะนำเกือบทุกครั้ง — ตั้งตัวเลือกแรกให้เป็นตัวที่แนะนำจริง ๆ

**เสร็จเมื่อ:** ทุกข้อในคำสั่งมีเจ้าของงานชัด และไม่มีทางแยกที่ยังต้องเดา

## 2 · อ่านด่านเดิมก่อนออกแบบ — ด่านคือสัญญาที่บังคับดีไซน์

บทเรียนแพงที่สุดของโปรเจกต์นี้: ดีไซน์ที่ดูสมเหตุสมผลอาจขัดสัญญาที่ด่าน 50 ชุดพึ่งอยู่

ตัวอย่าง — "กดยืนยันแล้วค่อยใช้" ฟังดูควร staging ไม่เขียน state
แต่ `brief-r11` ยิง `.value` ใส่ช่องวันที่แล้วเรียก `.onchange()` ตรง จากนั้นอ่าน `dPeriod()` **ทันที**
⇒ state ต้องเปลี่ยนทันที ปุ่มยืนยันคุมได้แค่ **การวาดจอ** · ถ้าไม่อ่านด่านก่อน จะรู้ตอนกระดานแดง

`grep -rn '<selector ที่จะแตะ>' tools/qa/suites/` ก่อนลงมือทุกครั้ง

**เสร็จเมื่อ:** รู้ว่าด่านชุดไหนแตะของที่จะแก้ และแต่ละชุดล็อกอะไรไว้

## 3 · เขียนด่านใหม่ก่อน แล้วค่อยแก้โค้ด

ชุดใหม่ตั้งชื่อ `<เรื่อง>-r<เลขรอบ>.js` · หัวไฟล์เขียนคำสั่งเจ้าของคำต่อคำ + รายการข้อที่ล็อก
ทดสอบสิทธิ์ = เรียกฟังก์ชันเขียนตรง ๆ ไม่ใช่ดูว่าปุ่มถูกซ่อน

## 4 · พิสูจน์ mutation ทุกข้อ

ทำตาม `famai-mutation` — ทุกข้อต้องแดงทีละตัว แล้วคืนไฟล์ให้เขียว
mutation ที่ยังเขียวคือ**ด่านอ่อน** ต้องแก้ด่าน ไม่ใช่ปล่อยผ่าน

**เสร็จเมื่อ:** ทุกข้อของด่านใหม่แดงได้ และบรรทัดที่แดงตรงกับข้อที่ตั้งใจ

## 5 · ดูด้วยตา — สกรีนช็อต 1440 และ 390 ทั้งสว่างและมืด

ด่านเขียวไม่ได้แปลว่าดูดี · รอบนี้ตาจับได้ที่ด่านจับไม่ได้: ตัวหนังสือหายทั้งแผงในธีมมืด ·
ช่องวันที่เก่าโผล่ข้างปฏิทิน · ปุ่มหลักตกไปอยู่ท้ายหน้ายาวบนมือถือ · อักษรย่อไทยเป็นสระลอย

```js
await p.evaluate(t=>{ document.documentElement.dataset.theme=t; }, 'dark');
```
ถ่ายทั้งสถานะ "ยังไม่ได้ยืนยัน" ด้วย ไม่ใช่แค่สถานะปกติ — สถานะกลางคือที่ที่ UI พังบ่อยที่สุด

## 6 · รันครบทุกชุด

`node tools/qa/suites/syntax.js` ก่อน แล้ว `node tools/qa/run.js` (~15-20 นาที)
ต้องเขียวครบ **ทุก** ชุดก่อน push — ชุดแดงโดยไม่ได้แก้อะไรตรงนั้น ให้สงสัยสภาพแวดล้อมก่อนโค้ด

## 7 · เอกสาร — สามที่ ทุกครั้ง

- `docs/04-design-system.md` §9x ใหม่ — **เหตุผล** ที่เลือกทางนี้ + กับดักที่เจอตอนเขียนด่าน
  (ส่วนนี้แหละที่รอบหน้าจะได้ใช้ ไม่ใช่รายการสิ่งที่ทำ)
- `docs/08-state-and-handoff.md` — บรรทัดเวอร์ชันใหม่ + จำนวนชุดด่าน
- `README.md` — เวอร์ชัน + จำนวนชุดด่าน

## 8 · commit + push

commit message ภาษาไทย: เจ้าของสั่งอะไร · แก้อย่างไร · **ทำไมเลือกทางนี้** · ตรวจอะไรไปแล้ว
`git push -u origin claude/start-b18xi3` · ห้ามเปิด PR เว้นแต่เจ้าของสั่ง
ห้ามใส่ชื่อรุ่นโมเดลลงใน commit / โค้ด / เอกสาร

## 9 · ตรวจ production จริง

เบราว์เซอร์ในกล่องออกเน็ตไม่ได้ — ดึงไฟล์ที่ deploy แล้วมาเปิดแบบ `file://` แทน

```bash
curl -s -o <scratchpad>/prod.html https://famai-web.vercel.app/index.html
```
```js
await p.goto('file://<scratchpad>/prod.html');   // แล้วขับด้วย Playwright ตามปกติ
```
ขับให้ถึง**พฤติกรรมที่เจ้าของสั่ง**จริง ๆ ไม่ใช่แค่เช็คว่าหน้าเปิดได้:
เก็บตัวเลขก่อน–หลังการกระทำ แล้วยืนยันว่ามันเปลี่ยนตามที่ควร + `pageerror` ต้องว่าง

**เสร็จเมื่อ:** ของบน production ทำสิ่งที่เจ้าของขอได้จริง วัดเป็นตัวเลขได้ ไม่ใช่ "เปิดได้"

## 10 · รายงานเจ้าของ

ภาษาไทย · เริ่มจากสิ่งที่เจ้าของจะเห็นเปลี่ยนบนจอ ไม่ใช่ชื่อฟังก์ชัน
ต้องมี: ตัวเลขจาก production จริง · ด่านที่แก้และเพราะอะไร · **สิ่งที่จงใจไม่แก้เพราะอยู่นอกที่สั่ง**
(ข้อสุดท้ายสำคัญ — เจ้าของจะได้เลือกเองว่าจะสั่งเพิ่มไหม)
